## 1. Abertura — o que você vai aprender e por quê

No fim do mini-projeto da trilha passada (5.6), você levou um serviço do reconhecimento ao comprometimento e conquistou um <GlossaryTerm term="foothold">foothold</GlossaryTerm> (o acesso inicial, de onde se executa comando no alvo). Mas, quando você rodou `id`, a resposta não foi `root`: foi `daemon`, uma conta de serviço sem poder nenhum. Você estava **dentro**, e ainda assim preso. Esse teto tem nome, e tirá-lo é todo um ramo da arte: a **escalação de privilégio**.

Este módulo é o mapa antes da viagem. Ele não ensina um vetor específico a fundo — isso vem nos próximos (6.2 a 6.6). Ele ensina o que você precisa saber **antes**: como o Linux e o Windows decidem quem pode o quê, por que esse sistema de poderes existe, e **onde**, na prática, ele costuma falhar. Sem esse mapa, enumerar uma máquina é olhar uma parede de saída sem saber o que é pista e o que é ruído. Com ele, cada linha de uma enumeração vira uma pergunta: *isto me dá um caminho para cima?*

## 2. Teoria aprofundada — o privilégio por dentro

### 2.1 O que é privilégio, e por que os sistemas separam poderes

<GlossaryTerm term="privilege escalation">Privilege escalation</GlossaryTerm> (escalação de privilégio) é passar de um nível de poder para um nível maior do que o que lhe foi concedido. Para entender a escalação, é preciso entender por que existe o degrau.

Um sistema operacional moderno não trata todos os programas igual. Ele separa o mundo em dois: o <GlossaryTerm term="kernel">kernel</GlossaryTerm> (o núcleo, que fala direto com o hardware e controla memória, disco e processos) roda num modo protegido do processador, onde tudo é permitido; os programas comuns rodam num modo restrito, onde cada acesso a disco, rede ou memória de outro processo precisa pedir licença ao kernel. Essa separação existe para que um erro (ou um ataque) num programa qualquer não derrube a máquina inteira nem leia o que não deve. É a primeira fronteira de privilégio.

Dentro do modo restrito há uma segunda separação: a de **contas de usuário**. Cada processo pertence a um usuário, e o kernel usa essa identidade para decidir o que ele pode tocar. Um usuário comum não lê os arquivos de outro, não mexe na configuração do sistema, não mata processos alheios. Existe, porém, uma conta acima de todas — <GlossaryTerm term="root">root</GlossaryTerm> no Linux, SYSTEM no Windows — para a qual essas checagens praticamente não valem. Ela precisa existir: alguém tem que poder instalar programas, criar usuários, ler qualquer log. O problema de segurança nasce daí: **se um atacante que entrou como usuário comum conseguir virar essa conta, todas as fronteiras caem de uma vez.**

Toda escalação é, no fundo, isto: explorar uma brecha para que o kernel passe a tratar o seu processo como se fosse de uma conta mais poderosa. A brecha pode ser uma configuração errada, um bug num programa que já roda com poder, ou uma credencial que você achou. O resto deste módulo é o catálogo dessas brechas.

Antes do catálogo, duas direções. A escalação <GlossaryTerm term="vertical privilege escalation">vertical</GlossaryTerm> é subir: de `www-data` para `root`, de usuário para administrador. É a que primeiro vem à cabeça. A <GlossaryTerm term="horizontal privilege escalation">horizontal</GlossaryTerm> é andar de lado: continuar no mesmo nível, mas assumir a identidade de **outro** usuário de igual poder — para ler os dados dele, usar o acesso dele a um terceiro sistema, ou agir em nome dele. Um IDOR (que você viu em 4.5) que te deixa ver o pedido de outro cliente é escalação horizontal. As duas quebram a fronteira que separava uma identidade da outra; por isso as duas contam.

### 2.2 O modelo do Linux: uid, root, SUID, sudo e capabilities

No Linux, toda conta é um número: o **uid** (user ID). O `root` é simplesmente o uid **0**, e o kernel tem no código a regra "uid 0 pula quase todas as checagens". Grupos são os **gid**. Quando um processo tenta abrir um arquivo, o kernel compara o uid/gid do processo com as permissões do arquivo (aquele `rwxr-xr--` do `ls -l` que você viu em 0.3) e decide.

Mas o uid de um processo não é um número só. O kernel guarda, entre outros, o uid **real** (quem iniciou o processo) e o <GlossaryTerm term="effective user ID">effective user ID</GlossaryTerm> (o uid efetivo, que é o que ele de fato usa para decidir cada permissão). Normalmente os dois são iguais. O que os separa é o bit **SUID**.

<GlossaryTerm term="SUID">SUID</GlossaryTerm> (set-user-ID) é um bit na permissão de um arquivo executável. Quando ligado, o programa roda com o uid efetivo do **dono do arquivo**, não de quem o executou. O exemplo canônico é o `passwd`: trocar sua senha exige escrever em `/etc/shadow`, um arquivo que só o root pode tocar. Como o `passwd` é SUID root, ao rodá-lo **você** passa a ter, por aqueles instantes, o poder de escrever ali. No `ls -l`, o SUID aparece como um `s` no lugar do `x` do dono: `-rwsr-xr-x`. O <GlossaryTerm term="SGID">SGID</GlossaryTerm> (set-group-ID) é o irmão para o grupo.

Essa é a primeira grande superfície: **todo binário SUID root é um trecho de código que roda como root a pedido de qualquer um.** Se ele tiver um bug (como o sudo de 2021, na seção 4) ou se puder ser levado a executar algo que você escolhe (o caso do `find -exec`, catalogado no <GlossaryTerm term="GTFOBins">GTFOBins</GlossaryTerm>), o seu uid efetivo vira 0.

O `root` tudo-ou-nada, porém, é grosseiro demais. Um servidor web precisa abrir a porta 80 (privilégio de root), mas não precisa do poder de formatar o disco. Para quebrar esse monólito, o Linux tem duas ferramentas:

- O <GlossaryTerm term="sudo">sudo</GlossaryTerm> dá poder **pontual**: o arquivo `/etc/sudoers` lista quais comandos cada usuário pode rodar como root. Bem configurado, é menor privilégio; mal configurado (um comando que pode virar shell, um `NOPASSWD` perigoso), é uma rampa direta para root. Você confere o seu com `sudo -l`.
- As <GlossaryTerm term="Linux capabilities">Linux capabilities</GlossaryTerm> fatiam o poder de root em dezenas de pedaços independentes. Em vez de ser root, um programa recebe só a capability `cap_net_raw` (abrir pacotes crus) ou `cap_net_bind_service` (abrir portas baixas). Você vê isso no `ping`: nas distribuições modernas ele não é mais SUID root, e sim um binário comum com a capability certa — você vai conferir isso na Missão 1. Uma capability dada a mais (`cap_setuid`, `cap_dac_override`) também é uma ponte para root.

Por fim, os serviços. Um servidor bem configurado não roda como root: roda sob uma conta dedicada de baixo privilégio — `www-data` para o Apache, `daemon` para outros. É por isso que o seu RCE no 5.6 caiu como `daemon`. Essa é uma defesa (o atacante não ganha a máquina de graça), mas também o ponto de partida da escalação.

### 2.3 O modelo do Windows: SID, UAC, tokens e integridade

O Windows resolve o mesmo problema com peças diferentes, que você viu no módulo 0.5. Toda conta e todo grupo são identificados por um <GlossaryTerm term="SID">SID</GlossaryTerm> (security identifier), não por um número simples. O equivalente ao root não é bem o Administrador: é o **SYSTEM** (SID `S-1-5-18`), a conta com que o próprio sistema e muitos serviços rodam, com poder acima até do administrador comum. Em pentest, o objetivo da escalação no Windows costuma ser chegar a SYSTEM.

Entre o usuário e o poder existem três mecanismos que importam para a escalação:

- O <GlossaryTerm term="UAC">UAC</GlossaryTerm> (User Account Control) faz com que, mesmo sendo administrador, você trabalhe por padrão com um **token filtrado** — um crachá rebaixado, de integridade Média. Só ao aprovar a elevação você recebe o token cheio, de integridade Alta. Escalar, aqui, muitas vezes é "contornar o UAC" para rodar algo já com o token cheio.
- Todo processo carrega um <GlossaryTerm term="access token">access token</GlossaryTerm> (token de acesso): um crachá que lista quem você é (seu SID), seus grupos e seus **privilégios** nomeados. Alguns privilégios são, na prática, chaves-mestras. O <GlossaryTerm term="SeImpersonatePrivilege">SeImpersonatePrivilege</GlossaryTerm> — dado a contas de serviço para que atendam clientes em nome deles — permite a <GlossaryTerm term="token impersonation">token impersonation</GlossaryTerm>: assumir o token de outra conta. Abusado, ele vira SYSTEM, por meio do que se chama <GlossaryTerm term="potato attack">potato attack</GlossaryTerm> (a família de técnicas Rotten/Juicy Potato, PrintSpoofer e afins). O `SeBackupPrivilege` lê qualquer arquivo; o `SeDebugPrivilege` mexe em qualquer processo. Você lista os seus com `whoami /priv`.
- O <GlossaryTerm term="integrity level">integrity level</GlossaryTerm> (nível de integridade) é um carimbo (Baixo, Médio, Alto, Sistema) que limita o que um processo escreve, independentemente do usuário. É mais uma fronteira que a escalação precisa vencer.

A lição a guardar: Linux e Windows são duas respostas para a **mesma** pergunta — como dar poder suficiente para o trabalho e nem um pingo a mais. Onde a resposta vaza, mora a escalação.

### 2.4 O princípio que amarra tudo: menor privilégio

Há um fio que costura as duas seções: o **princípio do menor privilégio** (<GlossaryTerm term="least privilege">least privilege</GlossaryTerm>). Cada conta, processo e usuário deveria ter exatamente o poder necessário para a sua função, e nada além. O SUID existe para dar poder pontual; o sudo, para dar poder nomeado; as capabilities, para fatiar o poder; as contas de serviço, para rodar sem poder. Todos são tentativas de aplicar menor privilégio.

E é por isso que **toda escalação é a exploração de uma violação do menor privilégio.** Reduza as classes a quatro e você tem o catálogo inteiro:

1. **Má configuração** — alguém deu poder a mais: um `sudoers` frouxo, um arquivo de root gravável por todos, uma pasta de serviço que qualquer um edita.
2. **Software vulnerável** — um programa que já roda com poder tem um bug: um binário SUID, um serviço, o próprio kernel (um <GlossaryTerm term="kernel exploit">kernel exploit</GlossaryTerm>).
3. **Credenciais** — uma senha, uma chave ou um hash de uma conta mais poderosa, esquecido num arquivo, no histórico ou na memória.
4. **Abuso de recurso legítimo** — um privilégio de token, uma capability ou um recurso do sistema usado para o que não era (a token impersonation da família Potato).

Guardadas essas quatro classes, qualquer enumeração passa a se encaixar numa delas.

## 3. Na prática da segurança — o mapa das superfícies

A teoria diz por que a escalação é possível. A prática responde **onde** procurar. As quatro classes da seção 2.4 se materializam em lugares concretos que todo pentester varre — e que o diagrama abaixo resume.

### 3.1 Onde a escalação mora no Linux

- **SUID/SGID fora do padrão.** A lista de binários SUID (via `find / -perm -4000 -type f 2>/dev/null`) sempre tem os suspeitos de sempre (`passwd`, `sudo`, `su`, `mount`). O que interessa é o que **não** deveria estar ali: um `find`, um `vim`, um `python`, um binário caseiro. O GTFOBins cataloga exatamente como cada um vira shell quando é SUID.
- **sudo mal configurado.** O `sudo -l` mostra o que você pode rodar como root. Um comando que abre um editor, um pager ou um shell (ou que o GTFOBins liste) é uma rampa.
- **Capabilities a mais.** `getcap -r / 2>/dev/null` lista binários com capabilities. `cap_setuid`, `cap_dac_override` e amigos levam a root.
- **`cron` e timers graváveis.** Uma tarefa agendada (<GlossaryTerm term="cron">cron</GlossaryTerm> ou timer do systemd) que roda como root e executa um script que **você** pode editar é um dos vetores mais limpos que existem: você reescreve o script e espera o root rodá-lo. É o coração da Missão 2.
- **PATH sequestrável.** Um programa privilegiado que chama outro só pelo nome (sem caminho completo) pode acabar rodando o **seu** binário, se você controlar o `PATH` — a versão Linux do que o 0.5 mostrou no Windows.
- **Serviço rodando como root** quando não precisava, e **credenciais em arquivos** (senhas em `config.php`, chaves em `.bash_history`, `.htpasswd` — como você saqueou no 5.6).
- **Kernel desatualizado.** Quando nada mais abre, um kernel antigo quase sempre tem uma falha local conhecida (a seção 4 traz uma).

### 3.2 Onde a escalação mora no Windows

- **Serviço com binário ou pasta gravável.** Se um serviço roda como SYSTEM e você pode sobrescrever o `.exe` dele (ou a pasta onde ele está), você troca o executável e, no próximo start, o seu código roda como SYSTEM. É o coração da Missão 3.
- **`unquoted service path`.** Um caminho de serviço com espaços e **sem aspas** (`C:\Program Files\...`) faz o Windows tentar executar `C:\Program.exe` primeiro — se você puder criá-lo, vira SYSTEM.
- **<GlossaryTerm term="AlwaysInstallElevated">AlwaysInstallElevated</GlossaryTerm>.** Com as duas chaves de registro ligadas, qualquer `.msi` roda como SYSTEM.
- **Tarefas agendadas** graváveis e <GlossaryTerm term="DLL hijacking">DLL hijacking</GlossaryTerm> (plantar uma DLL que um programa privilegiado carrega pela ordem de busca).
- **Privilégios de token.** `SeImpersonatePrivilege` (a família Potato), `SeBackupPrivilege`, `SeDebugPrivilege` — cada um é uma chave.
- **Credenciais** no registro, em `Unattend.xml`, no cofre, ou na memória do LSASS, e **drivers de kernel vulneráveis** (a seção 4 traz um).

### 3.3 O método: enumerar, listar, priorizar, explorar

Diante dessa parede de possibilidades, o profissional não sai tentando tudo. Ele segue um ciclo:

1. **Enumerar** tudo — à mão ou com um script. Os mais usados são o **linpeas** (Linux) e o **winpeas** (Windows), do projeto PEASS-ng, que varrem todas essas superfícies e colorem o que merece atenção. (Nos próximos módulos você vai rodá-los; aqui só precisa saber o que eles fazem.)
2. **Listar os candidatos** — cada achado que se encaixa numa das quatro classes.
3. **Priorizar.** Nem todo vetor é igual. Pesa-se três coisas: a **confiabilidade** (um script gravável rodado por `cron` é quase garantido; um kernel exploit pode falhar), o **ruído** (um exploit de kernel pode travar a máquina e acender alarmes) e a **estabilidade** (vou deixar o sistema de pé depois?). Um bom pentester prefere o vetor mais confiável e silencioso primeiro.
4. **Explorar** — e, de novo, enumerar a partir do novo nível.

<Callout variant="tip" title="A pergunta que organiza tudo">
Para cada linha de uma enumeração, pergunte: **isto é algo que eu controlo e que algo mais privilegiado usa?** Um arquivo gravável só importa se algo com poder o lê ou executa. Um binário SUID só importa se ele me deixa executar o que eu quero. A escalação vive sempre nesse cruzamento entre "o que eu toco" e "o que tem poder".
</Callout>

## 4. Casos reais — o que aconteceu no mundo

A escalação de privilégio não é teoria de laboratório: é um elo obrigatório de quase toda intrusão séria. Três casos verificados, um por superfície.

### Dirty COW — o kernel que todos tinham (2016)

A **CVE-2016-5195**, apelidada de **Dirty COW**, foi uma <GlossaryTerm term="race condition">race condition</GlossaryTerm> (condição de corrida) no arquivo `mm/gup.c` do kernel do Linux, no tratamento do mecanismo de *copy-on-write* (COW). Explorando a corrida, um usuário **local** comum conseguia escrever em uma área de memória que era só de leitura — e, com isso, alterar arquivos de root e virar root. A falha atingia os kernels Linux da série 2.x até a 4.x anteriores à **4.8.3**: ou seja, praticamente toda máquina Linux em produção na época, incluindo Android. Reportada por Phil Oester, foi publicada em **10 de novembro de 2016** e, segundo o próprio registro da CVE, já estava sendo **explorada ativamente** em outubro de 2016.

- **Impacto:** <GlossaryTerm term="local privilege escalation">escalação local</GlossaryTerm> confiável para root em quase todo o parque Linux instalado; a correção exigia atualizar o kernel (4.8.3+) e reiniciar.
- **Lição:** o <GlossaryTerm term="kernel exploit">kernel exploit</GlossaryTerm> é o último recurso e o mais poderoso — quando o kernel está velho, nenhuma configuração de menor privilégio no espaço do usuário segura a escalação. Manter o kernel atualizado é uma defesa de base.
- **Fonte:** [Registro CVE-2016-5195 (MITRE)](https://www.cve.org/CVERecord?id=CVE-2016-5195).

### Baron Samedit — o próprio sudo com o bug (2021)

Se o `sudo` é a ferramenta que dá poder pontual com segurança, o que acontece quando o bug está nele mesmo? Em **26 de janeiro de 2021**, a Qualys divulgou a **CVE-2021-3156**, apelidada de **Baron Samedit**: um *off-by-one* que levava a um *heap buffer overflow* no `sudo` e permitia a qualquer usuário local virar root — mesmo sem estar no `sudoers` — por meio de `sudoedit -s` e um argumento terminado em uma única barra invertida. Atingia as versões **1.7.7 a 1.7.10p9, 1.8.2 a 1.8.31p2 e 1.9.0 a 1.9.5p1**, corrigidas na **1.8.32** e na **1.9.5p2**. A falha vivia no código do sudo havia quase dez anos.

- **Impacto:** root local garantido em quase toda instalação Linux/Unix padrão, já que o `sudo` vem em praticamente todas e a condição independia de o usuário ter permissão de sudo.
- **Lição:** um binário SUID root é confiável só enquanto o código dele é — a superfície "SUID" inclui os próprios programas que confiamos. Atualizar o pacote (`apt upgrade`) foi a correção.
- **Fonte:** [Aviso de segurança do projeto sudo (Baron Samedit)](https://www.sudo.ws/security/advisories/unescape_overflow/).

### CLFS — o degrau de um ataque de ransomware (2023)

A **CVE-2023-28252** foi uma falha de *elevation of privilege* no driver **CLFS** (Common Log File System) do Windows — um *heap buffer overflow* (CWE-122) com nota CVSS **7.8**. Manipulando um arquivo de log (`.BLF`), um atacante que já tinha um acesso de baixo privilégio virava SYSTEM. O que a torna didática é o contexto: ela foi descoberta pela equipe GReAT da Kaspersky sendo usada como **zero-day** (falha ainda sem correção) em ataques reais, para elevar privilégio e então implantar o **ransomware Nokoyawa** em pequenas e médias empresas no Oriente Médio, na América do Norte e na Ásia. A Microsoft a corrigiu no Patch Tuesday de **11 de abril de 2023**, e a CISA a incluiu no catálogo de vulnerabilidades exploradas ativamente (KEV).

- **Impacto:** o elo que transformava um acesso inicial num comprometimento total da máquina, que então era criptografada pelo ransomware — a escalação como etapa necessária do ataque, não como curiosidade.
- **Lição:** no mundo real, a escalação quase nunca é o fim: é o meio. Entre "entrei" e "fiz o estrago" há sempre um "virei SYSTEM/root". Cortar esse elo (patch, menor privilégio, detecção) quebra a cadeia inteira.
- **Fonte:** [Registro CVE-2023-28252 (MITRE)](https://www.cve.org/CVERecord?id=CVE-2023-28252) e [análise da Kaspersky (Nokoyawa)](https://www.kaspersky.com/about/press-releases/2023_zero-day-in-microsoft-windows-used-in-nokoyawa-ransomware-attacks).

Este módulo não tem lab próprio: ele é conceitual, e a prática roda no **seu próprio WSL**, contra arquivos de treino que você mesmo gera. Você não vai *explorar* nada aqui (isso é dos próximos módulos) — vai treinar o olho que separa um vetor real de um ruído, que é a habilidade que faz toda a diferença depois.

**Objetivo:** ao terminar, você terá (1) visto, na sua máquina, o modelo de privilégio do Linux funcionando de verdade; (2) feito a triagem de uma enumeração Linux, achando o único vetor real no meio de distrações; e (3) feito o mesmo com uma enumeração Windows, identificando o caminho até SYSTEM. ### 5.2 Missão 1 — O modelo de privilégio no seu WSL (guiada)

Antes de olhar máquina de outro, veja a sua. Vamos tocar no modelo de privilégio do Linux com as próprias mãos. Rode, um a um:

```console
$ id
uid=1000(voce) gid=1000(voce) groups=1000(voce),27(sudo),...
$ grep '^root:' /etc/passwd
root:x:0:0:root:/root:/bin/bash
```

Repare no `0:0`: o `root` é o uid 0. É o número, não o nome, que dá o poder. Agora veja um binário SUID de verdade e o que o `s` significa:

```console
$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root 93640 ... /usr/bin/passwd
$ getcap /usr/bin/ping
/usr/bin/ping cap_net_raw=ep
```

Aquele `s` no lugar do `x` do dono é o SUID: o `passwd`, rodado por você, trabalha com o poder do root. E o `ping` mostra o outro modelo: nas distribuições modernas ele não é mais SUID root — ganhou só a capability `cap_net_raw`, o pedaço de poder de que precisa.

Agora crie o seu próprio arquivo SUID de teste e observe o bit:

```console
$ cp /bin/true /tmp/privesc-6.1/suid-demo
$ chmod 4755 /tmp/privesc-6.1/suid-demo
$ ls -l /tmp/privesc-6.1/suid-demo
-rwsr-xr-x 1 voce voce ... /tmp/privesc-6.1/suid-demo
$ find /tmp/privesc-6.1 -perm -4000 -type f
/tmp/privesc-6.1/suid-demo
```

Você acabou de fazer o que o pentester faz primeiro: marcar o SUID (`chmod 4755`) e **encontrá-lo** com `find -perm -4000`. Observe que o `4` na frente do `755` é justamente o bit SUID.

A flag da Missão 1 junta três coisas que você acabou de ver: o **modo em octal** que você deu ao `suid-demo`, a **letra** que apareceu no lugar do `x` do dono no `ls -l`, e o **nome** do programa SUID root que troca a senha de um usuário comum. Monte `FLAG{octal-letra-programa}`.

### 5.3 Missão 2 — Triagem de uma enumeração Linux (desafio)

Abra o `linux-enum.txt` que você gerou:

```console
$ cat /tmp/privesc-6.1/linux-enum.txt
```

Você é o `www-data` do host `web-01`. A enumeração tem quatro achados que *parecem* promissores. Seu trabalho é dizer qual é o **vetor de escalação real** — e, de quebra, perceber por que os outros três não levam a nada. Lembre da pergunta da seção 3.3: *o que eu controlo e que algo mais privilegiado usa?*

<Hint title="Dica 1 — elimine os ruídos">
- O `sudo -l` deixa você rodar `/usr/bin/id` como root. `id` roda como root, sim — mas só imprime a identidade e sai. Ele te dá um shell? (Pense no caso do `find` da seção 3.1.)
- A lista de SUID só tem os suspeitos de sempre (`passwd`, `mount`, `chsh`, `sudo`, `su`). Nada de `find`, `vim`, `python`. Vetor?
- O `config.php` é gravável por você (`rw-rw-rw-`). Mas quem, com poder, **executa** um `config.php`? Ele é lido pelo PHP como dado, não rodado como root.
</Hint>

<Hint title="Dica 2 — ache o cruzamento">
Olhe ao mesmo tempo a lista de **arquivos graváveis** e a lista de **tarefas agendadas**. Existe um arquivo que aparece nas duas? Um que **você** pode editar e que o **root** executa sozinho, de tempos em tempos?
</Hint>

<Solution title="Solução">
O vetor é o `/opt/scripts/backup.sh`. Ele aparece no cruzamento das duas listas:

- em **Arquivos graváveis**, está como `-rwxrwxrwx` — ou seja, modo **777**, qualquer um pode reescrevê-lo;
- em **Tarefas agendadas**, o `cron` o executa **como root**, a cada minuto (`*/1`).

Então: você reescreve o `backup.sh` com o que quiser, espera no máximo um minuto, e o root roda o seu código. É o vetor "cron + script gravável", um dos mais confiáveis que existem. Os outros três são ruído: `sudo id` não dá shell, o SUID é todo padrão, e ninguém privilegiado executa o `config.php`.

A flag junta, nessa ordem, o **basename** do script (o `backup.sh`), o **usuário** que o executa (visto na linha do `cron`) e o **octal** do `-rwxrwxrwx` que o torna gravável por todos. Monte-a você mesmo no formato `FLAG{script-usuario-octal}` que o cartão pede.
</Solution>

### 5.4 Missão 3 — Triagem de um token no Windows (desafio)

Agora o `windows-enum.txt`. Você caiu na conta de serviço `svc_web` do host `WIN-APP01` e quer chegar a SYSTEM.

```console
$ cat /tmp/privesc-6.1/windows-enum.txt
```

Há **dois** caminhos independentes até SYSTEM escondidos nessa saída. Ache os dois.

<Hint title="Dica 1 — o token">
Releia o `whoami /priv`. Um dos privilégios habilitados é a chave-mestra das contas de serviço — o que a seção 2.3 ligou à família Potato. Qual é o nome exato dele (com as maiúsculas)?
</Hint>

<Hint title="Dica 2 — o serviço">
Cruze o `sc.exe qc` com o `icacls`. O serviço roda como quem (`SERVICE_START_NAME`)? E a pasta do binário dele — quem tem `(F)`, controle total, sobre ela? Se o grupo `Users` pode escrever na pasta do `.exe` que roda como SYSTEM, você troca o `.exe`.
</Hint>

<Solution title="Solução">
Os dois caminhos:

1. **Token:** o `whoami /priv` mostra `SeImpersonatePrivilege` com `State: Enabled`. Com um ataque da família Potato, a conta de serviço impersona o token do SYSTEM e vira SYSTEM.
2. **Serviço gravável:** o `UpdaterSvc` roda como `LocalSystem` (no `sc.exe qc`), e o `icacls` mostra `BUILTIN\Users:(OI)(CI)(F)` na pasta `C:\Program Files\Updater` — ou seja, você pode sobrescrever o `updater.exe`. No próximo start do serviço, o seu executável roda como SYSTEM.

A flag junta o **privilégio** do caminho 1 (o nome exato, com as maiúsculas, que aparece no `whoami /priv`) e o **nome do serviço** vulnerável do caminho 2 (o do `sc.exe qc`). Monte-a no formato `FLAG{privilegio-servico}` que o cartão pede.
</Solution>

## 6. Variações e aprofundamento

**Vertical e horizontal, de novo e mais fundo.** A horizontal é fácil de subestimar. Virar outro usuário do mesmo nível raramente parece "escalação", mas em uma rede corporativa é ela que move o ataque: de um usuário qualquer para o usuário que tem acesso ao servidor de arquivos, dele para o que administra o backup, e assim por diante. Em Active Directory (Trilha 7), quase tudo é escalação horizontal encadeada até cair numa conta que, por acaso, é administradora do domínio. A fronteira entre horizontal e vertical é mais borrada do que parece.

**Contêiner não é host.** Com a popularização do Docker, um engano virou epidemia: achar que ser <GlossaryTerm term="root">root</GlossaryTerm> dentro de um <GlossaryTerm term="container">contêiner</GlossaryTerm> é ter o host. Não é. O contêiner isola o processo em <GlossaryTerm term="namespace">namespaces</GlossaryTerm> próprios; root ali é root naquele mundo, não na máquina. Escapar para o host é outra escalação, que depende de uma brecha: o contêiner rodar como `privileged`, montar o `docker.sock` (justamente a regra de isolamento inegociável que o CLAUDE.md deste projeto proíbe), receber capabilities a mais, ou um bug no kernel compartilhado. Reconhecer essa fronteira muda o que você tenta a seguir.

**As camadas que atrapalham a escalação.** Linux e Windows têm defesas que não impedem a escalação, mas a dificultam: no Linux, o **SELinux** e o **AppArmor** confinam o que cada processo pode fazer mesmo sendo root, e o **seccomp** corta chamadas de sistema; no Windows, o **integrity level** e o **UAC**. Um vetor que funcionaria "no papel" pode esbarrar nelas — e um bom pentester nota a camada antes de perder uma hora.

**Living off the land.** Quando dá, o atacante prefere não trazer ferramenta nenhuma: usa o que já está na máquina. No Windows, os binários legítimos que podem ser subvertidos estão catalogados no **LOLBAS**; no Linux, os SUID/sudo exploráveis, no GTFOBins. Essa escolha — o <GlossaryTerm term="living off the land">living off the land</GlossaryTerm> — é mais silenciosa e é o padrão em operações maduras.

**Kernel vs. espaço do usuário.** O kernel exploit (Dirty COW) é o martelo: funciona quando tudo mais falha, mas é arriscado (pode travar a máquina) e barulhento. A escalação por configuração (o `backup.sh` da Missão 2) é o bisturi: silenciosa, estável, confiável. A experiência está em preferir o bisturi e guardar o martelo.

## 7. Erros comuns

- **"Roda como root, então me dá root."** Não. O que importa é se o programa te deixa **executar algo seu** como root (o `find -exec` dá; o `id` não). Confundir "privilegiado" com "explorável" faz perder horas num beco.
- **"Sou root no contêiner, ganhei a máquina."** Já visto na seção 6: root no contêiner ≠ root no host. Cheque a fronteira antes de comemorar.
- **Pular direto para o kernel exploit.** O iniciante baixa um exploit de kernel e roda de cara. Ele pode travar a máquina (péssimo num teste autorizado) e acender todo alarme. Esgote primeiro os vetores de configuração, mais confiáveis e silenciosos.
- **Enumerar demais e ler de menos.** Rodar o linpeas e olhar só o que está em vermelho. Metade dos vetores reais está no cruzamento de duas seções (um arquivo gravável **e** uma tarefa que o executa) — e nenhum script pinta esse cruzamento para você.
- **No Windows, confundir Administrador com SYSTEM.** Chegar a administrador não é o fim: com o UAC, o seu token ainda é filtrado, e há coisas que só o SYSTEM faz. O objetivo costuma ser SYSTEM.
- **"Não achei nada, a máquina é segura."** Quase sempre quer dizer "não enumerei direito". Faltou olhar os timers do systemd, as capabilities, o histórico de comandos, as variáveis de ambiente de um processo privilegiado.

## 8. Boas práticas e segurança

A escalação é a etapa que transforma um incidente pequeno (um RCE numa conta de serviço) num desastre (controle total). Cortá-la é das defesas de maior retorno — e quase tudo se resume a aplicar o menor privilégio de verdade.

**No Linux:**

- **Rode serviços com contas dedicadas e sem privilégio.** Um RCE que cai como `www-data` em vez de `root` já é meia batalha ganha. Foi o que segurou o ataque do 5.6 no `daemon`.
- **Reduza o conjunto SUID.** Liste o que é SUID (`find / -perm -4000`) e tire o bit do que não precisa (`chmod u-s`). Prefira capabilities a SUID root quando possível.
- **Trave o `sudoers`.** Nada de `NOPASSWD` para comandos que abrem shell, editor ou pager. Dê o comando mais específico possível, nunca `ALL`.
- **Endureça os serviços com o systemd.** Opções como `NoNewPrivileges=yes` (impede o processo e os filhos de ganharem privilégio, inclusive via SUID), `ProtectSystem=strict` e `PrivateTmp=yes` fecham superfícies inteiras de uma vez.
- **Mantenha o kernel e os pacotes atualizados.** `apt upgrade` é o que fecha o Dirty COW e o Baron Samedit. Um kernel velho anula todo o resto.

**No Windows:**

- **Corrija as permissões de serviços.** Nenhum serviço que roda como SYSTEM deve ter o `.exe` ou a pasta graváveis por `Users`. Ponha aspas nos caminhos (acaba o `unquoted service path`).
- **Rode serviços como contas virtuais ou gMSA**, não como `LocalSystem`, quando o serviço não precisar desse poder.
- **Tire privilégios de token perigosos** (`SeImpersonate`, `SeDebug`) das contas que não precisam deles, e deixe o **UAC** no nível mais alto.
- **Desligue o `AlwaysInstallElevated`** (ele quase nunca deveria estar ligado) e use o **LAPS** para que cada máquina tenha uma senha de administrador local única.
- **Mantenha o patch em dia.** A CLFS de 2023 fechou no Patch Tuesday; máquinas atrasadas é que viraram ransomware.

**Nos dois — detecção.** Menor privilégio reduz a superfície; a detecção pega quem passou mesmo assim. No Linux, o **auditd** pode registrar execução de binários SUID e mudanças em `/etc/sudoers`. No Windows, o **Sysmon** registra criação de processos, e vale alertar quando um processo de integridade Alta/Sistema nasce de um pai de baixo privilégio, ou quando o binário de um serviço muda. A escalação costuma deixar esse rastro — um processo "pulando" de nível — e é nele que o <GlossaryTerm term="blue team">blue team</GlossaryTerm> mira.

<Callout variant="info" title="A assimetria que favorece o defensor">
O atacante precisa de **uma** superfície aberta para escalar; o defensor que fecha o `sudoers`, tira o SUID a mais, atualiza o kernel, corrige as ACLs dos serviços e liga a detecção força o atacante a acertar todas. É a mesma lógica de defesa em profundidade do 5.6: várias camadas imperfeitas valem mais que uma perfeita, porque o atacante tem de vencer todas e o defensor só precisa de uma que segure.
</Callout>

## 10. Resumo e glossário

**Pontos-chave:**

- Escalação de privilégio é o elo entre o acesso inicial (foothold) e a pós-exploração: sair de uma conta de baixo privilégio e chegar a root (Linux) ou SYSTEM (Windows). Pode ser **vertical** (mais poder) ou **horizontal** (outra conta de mesmo nível).
- Os dois sistemas respondem à mesma pergunta — dar o poder mínimo necessário — com peças diferentes: no Linux, uid/root, SUID/SGID, sudo e capabilities; no Windows, SID, UAC, tokens/privilégios e integridade.
- Toda escalação é a exploração de uma violação do menor privilégio, em uma de quatro classes: **má configuração, software vulnerável, credenciais ou abuso de recurso legítimo**.
- O vetor real vive no cruzamento entre **o que você controla** e **o que tem poder**. A prática é enumerar, listar candidatos, priorizar (confiabilidade, ruído, estabilidade) e explorar.
- A defesa é o menor privilégio aplicado de verdade (contas de serviço sem poder, SUID enxuto, sudoers travado, serviços endurecidos, patch em dia) somado à detecção do "pulo" de nível.

```text
# cruze: arquivos graváveis  x  algo privilegiado que os usa

```
